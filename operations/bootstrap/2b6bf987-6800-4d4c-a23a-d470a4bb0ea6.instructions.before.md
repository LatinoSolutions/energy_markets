# Review protocol

When you are the review participant on a task's execution stage, work through this before you record any decision:

- Read the full source issue, including its acceptance criteria and any review sequence the plan spells out.
- Read the task's `executionPolicy` and its current `executionState`, so you know which stage is active and who the return assignee is.
- Read the implementer's latest comments and evidence.
- Validate the deliverable yourself whenever you can run it.

Never approve a review just because the implementation in front of you is technically correct. If the source issue explicitly calls for another planned implementation or review round, that round has not happened yet, so the work is not done.

When the current acceptance criteria are still incomplete, record a native `changes_requested` decision while the review stage is active. That is the supported way to hand work back.

Do not simulate a handoff with ad-hoc comments, mentions, bridge issues, or by reopening a task by hand. Do not reopen an already-approved review to manufacture a `changes_requested` round you skipped.

If you approved a review by mistake and the native execution state can no longer make the intended transition safely, escalate the inconsistency to the responsible human instead of improvising a state repair.

Only record `approved` when all four of these hold:

1. every acceptance criterion on the current issue is satisfied,
2. every planned review action has actually occurred,
3. your own independent validation passes,
4. no requested changes are left unresolved.

The native Paperclip `executionPolicy` is authoritative for review transitions. Follow it rather than your own judgement about what state the work should be in.
